# アーキテクチャとデータ フロー

> **正規の英語ソース:** [ARCHITECTURE.md](../../ARCHITECTURE.md). このローカライズされたドキュメントには、正確なコマンド、パス、キー、ステータス値、ハッシュ、ファイル名が保存されています。技術的な表現が異なる場合は、英語のソースを使用してください。


RandomDay は 1 つの制限付きジョブを所有しています。つまり、現在のプロセス中にそのプロファイルがアクティブであると記述せずに、将来の開始に備えて完全なサンドボックス プロファイルを準備します。アクティブなプロファイルは、UE4SS が開始される前に Abiotic Factor がロードしたサンドボックス ファイル内のマーカーから取得されます。 RandomDay準備されたプロファイルは、次回の再起動用に別の検証されたファイル状態になります。

<a id="package-modes"></a>
## パッケージ モード

リリース ビルダーは、まったく同じソース ホワイトリストから 2 つの ZIP を生成し、`RandomDay/.randomday_mode`それぞれに異なる値を設定します。

| モード | プライマリ出力 | 自動外部書き込み |
|---|---|---|
| `dedicated_server` | 解決された専用サーバー`SandboxSettings.ini` | プライマリ サンドボックス、意図的に構成されたミラー、および認識されたオプションのアダプター。 |
| `singleplayer_manual` | `RandomDay/runtime/singleplayer_manual/SandboxSettings.ini` | RandomDay フォルダの外には存在しません。ミラーとアダプターは無効になります。 |

`RandomDay/.randomday_version` と `RandomDay/.randomday_mode` は生成されたパッケージ マーカーです。 `RandomDay/Scripts/ax_core/version.lua` はそれらを読み取ります。オペレータはインストール後にこれらを編集してはなりません。

<a id="session-modes"></a>
## セッション モード

パッケージ モードは、RandomDay が書き込む場所を制御します。 `experience.mode`対象のライフサイクルについては、別途説明します。

| セッション モード | パッケージ | ライフサイクル コントラクト |
|---|---|---|
| `persistent_dedicated` | 専用 | 長期にわたる永続的なファミリーと 17 ポジションの日順を再開します。  |
| `temporary_dedicated` | 専用 | 起動間のキュー順序を維持しながら、各起動を制限付きプレイ セッションとして扱います。 |
| `singleplayer_lan` | シングルプレイヤー マニュアル | オペレーターが選択したワールドの MOD ローカル ファイルを生成します。保存検出や自動コピーはありません。 |

`auto` は、専用パッケージ内の `persistent_dedicated` と `singleplayer_lan` マニュアル パッケージに含まれています。セッション モードはエンジン境界を変更しません。RandomDay が実行される前に、現在のプロセスはすでにサンドボックスをロードしています。

<a id="startup-path"></a>
## スタートアップ パス

1. UE4SS は `RandomDay/Scripts/main.lua`.
2. エントリ ポイントは 1 つの`RandomDay/`ルートを解決し、`Scripts/ax_core/init.lua`.
3. `init.lua`ロード構成、プロファイル、カレンダー、ライター、アダプター、ステータス、Web エクスポート、およびプレーヤー メッセージ モジュール。無効なパッケージ モードまたは無効なトランザクション セーフティ ロックは拒否されます。また、パッケージ互換のセッション モード、開始日モード、設定された開始日、および日進行モードも検証します。
4. すべてのファミリ ビルドは、`sandbox.profile_overrides` を検証します。プロファイル全体の 4 つの選択肢は、`Scripts/ax_config/server.lua`から family/day 値の後、残りの不変ルールの前に適用されるため、準備されたすべてのプロファイルは同じ設定された選択肢を使用します。
5. ランタイムおよび Web 出力のルートは、解決された mod フォルダーに固定されます。シングルプレイヤー モードは、選択前に 1 つの MOD ローカル出力に削減されます。
6. `ax_cycle/calendar.lua` は、サンドボックス マーカーと回復可能なローテーション状態を読み取り、このゲーム プロセスに対して 1 つのactive/prepared決定を作成します。
7. `ax_sandbox/writer.lua` 準備されたプロファイルをシリアル化して検証し、選択されたターゲットに対してトランザクション置換を使用します。
8. ローテーション状態はコミットされます。サンドボックス トランザクションが成功した後にのみ。状態コミットの失敗は低下します。サンドボックスとキューの状態が一致しないため、アダプターと準備済みプレーヤーのメッセージングは​​スキップされます。
9. 専用モードでは、`ax_external/bridge.lua` はアクティブなプロファイルに対してオプションのアダプターを評価します。最初のブートストラップ中はアクティブなマーカーが存在しないため、準備されたconfigured/random開始日プロファイルが使用可能な唯一のアダプター マッピングです。
10. ランタイム JSON/text ステータスと HTML/JSON Web ビューは、同じ決定に基づいて書き換えられます。プレーヤー通知は最後にインストールされます。

デフォルトでは、起動時にこのシーケンスが 1 回実行されます。`cycle.check_interval_ms=0` は起動時にこのシーケンスを 1 回実行します。オペレーターが正の間隔を指定し、UE4SS が`LoopAsync`、後のコールバックはプロセスが所有する選択を再利用します。その選択を修復または再エクスポートすることはできますが、同じプロセス中に別の日を選択しないでください。

<a id="rotation-state-machine"></a>
## 回転ステート マシン

| 選択状態 | エントリ条件 | 準備された結果 | 安全な回復 |
|---|---|---|---|
| `bootstrap_prepare_first_family_start_day` | アクティブなマーカーがなく、回復可能ではありません準備済みの状態。 | 新しく永続化された日順で設定された、またはランダムに選択された最初の位置。 | 既存のセッションを実行し続けます。 `prepared_ready=true`. |
| `active_marker_found_family_locked_prepare_next_day` | アクティブな日は保存されたオーダーの最後のポジションではありません。 | 同じファミリー内の次の保存されたポジション。 | 永続化が失敗した場合は、サーバーを停止したままにし、サンドボックスとローテーションの状態を調整します。 |
| `active_marker_found_completed_run_prepare_next_unused_family` | アクティブな日は、保存されたオーダーの最後のポジションです。 | 次の適格なファミリー実行の新しい注文の最初の位置。 | 再起動する前に新しい注文を確認してください。family/day/order |
| `state_recovery_rewrite_prepared_profile_no_reroll` | アクティブなマーカーはありませんが、回転状態は準備されたプロファイルに名前を付けます。 | 同じキューに入れられたプロファイルが再構築されます。 | 状態ファイル。再ロールを強制するためにそれらを削除しないでください。 |
| `supervision_reconfirm_prepared_profile_no_advance` | 後のコールバックは同じプロセスで実行されます。 | 同じ準備されたプロファイル。 | 最初の失敗したステージを診断します。繰り返されるコールバックは新しい選択ではありません。 |

`selected_run` は常に使用します。 `selected_family`. `rotation_run` は、設定された対象となる注文を消費します。 `non_repeating_random_run` は残りの対象となるファミリーから選択し、すべてが完了した後に新しいプールを開始します。どのモードでも、`day_order` 内の 17 個の固有の日 ID がすべて完了するまで、1 つのファミリーが維持されます。シーケンシャル モードは、構成された開始日が 1 日目ではない場合、17 日目以降にラップされます。非繰り返しランダム モードでは、1 つの順列が保存され、リカバリ中にそれが再ロールされることはありません。

<a id="sandbox-transaction"></a>
## サンドボックス トランザクション

ライターは、すべてのキーを正規の順序でレンダリングし、書き込み前にタイプ、範囲、固定ルール、マーカー値、プロファイル ID を検証します。置換は次の順序に従います。

1. 安全な場合にのみ、古い保留中のファイルを削除します。
2. 既存のリカバリ サイドカーを保存または停止します。
3. 保留中のバイトを書き込みます。
4. 保留中のファイルを読み取って検証します。
5. ターゲットが存在する場合、検証済みのオペレーション バックアップを作成します。
6. オリジナルをトランザクション ロールバック ファイルとして保持します。
7. 保留中のファイルをプロモートします。
8. 実稼働ファイルを読み取り、検証します。
9. プロモートまたは実稼働の検証が失敗した場合は、保持されているオリジナルを復元します。
10. リカバリ データを保持し、クリーンアップを検証できない場合は失敗を報告します。

最初の書き込みでは同じpending/readback/validationパスが使用されます。元のターゲットがない場合、復元するものは何もないため、最初の書き込みの失敗を元のファイルのリカバリとして報告してはなりません。

<a id="adapter-boundary"></a>
## アダプターの境界

公開した場合、アダプターは、個別にインストールされた MOD のRandomDay-owned個別にインストールされた MOD のパッチ定義。ブリッジにはまず、認識されたターゲット パスと完全な調署名が必要です。既存の割り当てのみにパッチを適用し、操作のバックアップを作成し、計画されたすべてのファイルを 1 つのトランザクションとして適用し、ステップが失敗した場合は影響を受けるすべてのターゲットをロールバックします。ターゲットの欠落や互換性のなさは、通常のオプションの結果です。

RandomDay は、サードパーティのコードをパッケージにロードしません。フィクスチャバック レイアウトは、RandomDay'sパーサーとトランザクションの動作。サードパーティのリリースがゲーム プロセスで値をロードまたは使用したということではありません。

<a id="output-boundary"></a>
## 出力境界

ランタイム ファイルは以下に生成されます`RandomDay/runtime/` と `RandomDay/web_export/`; none はリリース ZIP 入力です。ステータス ライターは、パブリック JSON診断。完全なパス、スキーマ、ケイデンス、および保持マップは、[ランタイム ファイルとステータス](%E3%83%A9%E3%83%B3%E3%82%BF%E3%82%A4%E3%83%A0_%E3%83%95%E3%82%A1%E3%82%A4%E3%83%AB.md).

<a id="failure-ownership"></a>
## 障害の所有権

| 失敗したステージ | 所有者に見える結果 |
|---|---|
| プロファイルまたはINI検証 | 本番環境への書き込みは試行されません。 |
| 保留中 write/readback | 既存の実動バイトはそのまま残ります。 |
| 操作のバックアップ | 置換は、オリジナルが移動される前に停止します。 |
| プロモーションまたは本番環境の検証 | 自動復元が試行され、その結果が報告されます。 |
| 回転状態の永続性 | 準備されたサンドボックス バイトは存在する可能性がありますが、遷移は低下しており、adapters/messages はスキップされます。 |
| アダプターの互換性 | ターゲットは`not_installed` または `skipped_incompatible`. |
| アダプター write/readback | 可能な場合、変更されたアダプター ターゲットはすべて復元されます。 |
| ステータスまたは Web エクスポート | サンドボックスの結果は引き続き信頼できます。出力の失敗はログに記録されるため、成功レポートとして扱ってはなりません。 |

リカバリについては [操作](%E6%93%8D%E4%BD%9C.md)、症状優先チェックについては [トラブルシューティング](%E3%83%88%E3%83%A9%E3%83%96%E3%83%AB%E3%82%B7%E3%83%A5%E3%83%BC%E3%83%86%E3%82%A3%E3%83%B3%E3%82%B0.md)に従ってください。

<a id="evidence-limit"></a>
## 証拠の制限

ローカルの Lua フィクスチャ スイートは、ソースの動作、生成されたプロファイルの不変条件、トランザクション ブランチ、出力形状、およびパッケージ境界を証明できます。これは、現在の Abiotic Factor ビルドを証明するものではありません。 UE4SS リリース、特定のサーバー パネル、あらゆるディスプレイ サイズ、またはテストされていないサードパーティの MOD バージョン。これらの主張には、 `not tested`指定された互換性の実行が記録されるまで残ります。
